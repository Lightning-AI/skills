# Pass data between pipeline jobs

Use the two-step example in [the skill](../SKILL.md#python-sdk). Create a managed
folder with `Teamspace.new_folder(..., location=FolderLocation.CLOUD_AGNOSTIC)`
before launching jobs, or select an existing folder. Creating a directory inside
a job alone can leave files on that job's local disk: a later job cannot read them.

Both jobs use `/teamspace/lightning_storage/<folder>/<run-prefix>/...`. Keep
`shared_filesystem=False` on Lightning Cloud image jobs. Managed storage handles
the persistence; `wait_for=["prepare"]` handles execution order. Close output
files before the producer exits. A marker generated by the producer and read back
by the consumer proves the handoff better than both jobs printing a constant.

For a branched DAG, give independent steps `wait_for=[]`, write distinct output
paths, and make the consumer wait for all producers. Prefer an existing managed
folder with a unique prefix per execution so repeated runs cannot overwrite each
other. Keep source data and final outputs outside disposable test prefixes.

## Download and verify

After `PIPELINE_STATE_COMPLETED`, check that both statuses have distinct
`resourceId` job IDs. Set `$RUN`, `$TS` and `$PID` from submission/API readback.
Set `$FOLDER` to the folder created for this test; include any run prefix in `$URI`.

```bash
URI="lit://$TS/lightning_storage/$FOLDER"
lightning ls --json "$URI"
lightning cp "$URI/summary.json" ./summary.json
lightning pipeline logs download "$RUN" prepare --teamspace "$TS"
lightning pipeline logs download "$RUN" consume --teamspace "$TS"
```

The log command writes `job-prepare.log` / `job-consume.log`. Use a separate local
directory for each run. Check the downloaded summary's counts/values and compare
its marker with the producer's log. A successful submission or an empty download
is insufficient. If the consumer cannot find a file, verify the folder existed
before job creation, then inspect producer logs and list this exact storage URI.

## Remove disposable data

Download evidence first. Follow [pipeline cleanup](operations.md#cleanup) for
the exact run and jobs. If `$URI` points to a run subdirectory inside a managed
folder, remove that test prefix with `lightning rm -r "$URI"`.

If `$URI` is the managed folder itself, recursive removal requests deletion of
the folder registration and backing storage; it can leave files readable until
asynchronous deletion runs. Remove the test's files individually for immediate
cleanup. For the entrypoint example:

```bash
lightning rm "$URI/data.json"
lightning rm "$URI/summary.json"
lightning ls --json "$URI"
```

The final listing should be empty or report that the path does not exist. Some
versions omit empty folders from listings. Never delete the shared parent folder
when only a run subdirectory belongs to this test. If the test created a managed
folder, record its connection ID before use and delete that exact registration
after clearing its contents:

```bash
lightning api "/v1/projects/$PID/data-connections" -q '.dataConnections[] | {id,name,state}'
CONNECTION='verified-test-folder-connection-id'
lightning api "/v1/projects/$PID/data-connections/$CONNECTION" -X DELETE
lightning api "/v1/projects/$PID/data-connections/$CONNECTION"
```

Managed-folder deletion can be deferred by storage retention. The registration
can still show `CREATED` after DELETE succeeds. Report empty data and pending
registration removal separately; do not repeatedly submit deletes or infer
success from an unrelated HTTP error.
